# Verifier-fingerprint capture provenance

What the captures under `Zcash/Snark/Fixtures/` are, where they come from, and how to
reproduce them. The layout itself is described in `README.md`; what these captures check is each
family's `Boundary.lean` statement of record,
`nonInteractiveFingerprint_matches_derived`. For the unrelated circuit-side dumps see
`Zcash/Circuits/Fixtures/PROVENANCE.md` — the two pipelines share no artifact and no tooling.

Unlike those dumps, these captures have no missing-lineage problem: all four families — the
honest pair and the two match-only families, each of the latter with its raw `proof-bytes.hex`
sibling — regenerate from a pinned public release via
`scripts/regenerate-fingerprint-fixtures.sh`, which CI runs (`fixtures.yml`) to enforce every
committed artifact byte-for-byte.

## The capture sources

The random fixture families (the `Random/` subfolder of `SingleAction` and `MultiAction`)
are captures of the deployed halo2 verifier run on **random proof
strings**. They are generated by the same released pipeline as the honest captures — the
`verifier-fingerprint` feature of orchard, forwarding to `halo2_proofs`'
`unstable-verifier-fingerprint` — and, since zcash/halo2#924 and zcash/orchard#541 were
merged upstream and released, the capture tooling itself is released too: it ships in
`halo2_proofs` 0.3.5 and orchard 0.15.5. There is therefore exactly one pin, a release tag,
and no fork, unreleased branch, or `[patch.crates-io]` override anywhere in the pipeline.
Nothing in either release is deployed code: the capture additions extend the dev/test tooling
only, behind an unstable feature flag.

### The capture changes

`halo2_proofs` 0.3.5 carries the following reviewed source changes (zcash/halo2#924 and its
follow-ups, merged as `475e180e` and released as tag `halo2_proofs-0.3.5`):

**halo2 #924 — "Add a match-only Lean fixture exporter for non-accepting
captures"** — refactors `dump_vesta_lean_fixture`
(`halo2_proofs/src/plonk/fingerprint/vesta_lean.rs`) into a private mode-parameterized core
with two public wrappers. The honest exporter is unchanged in behavior and output. The new
`dump_vesta_lean_fixture_match_only` differs in exactly three places: the identity fail-fast
inverts (the captured MSM must **not** be the identity), the `capturedMsm_eval_eq_zero` /
`assembledMsm_eval_eq_zero` theorems are not emitted, and the generated header marks the
fixture as a match-only capture. Coordinate ordering, on-curve validation, URS emission,
instance-commitment re-derivation, schedule entries, and the slot-reconstruction and
term-count guards are shared with the honest path, so regeneration stays bit-reproducible in
both modes. Two integration tests cover the match-only render and the inverted fail-fast.

**"chore: make the exported fixture claim only what was captured"** —
emits the verifying key's actual `num_instance_columns` count into the generated Lean
`Shape`, defines `capturedNumInstanceColumns` through that field so the two names cannot
drift, and narrows the generic match-only header: the exporter attests only that the
verifier completed with a non-identity MSM, leaving random-input provenance to its caller.
The Orchard driver below supplies and documents that provenance.

**"chore: more 924 followups"** — makes fixture-mode dispatch
exhaustive, repairs the i686 CI package-index setup, and makes each match-only fixture
self-certify its mode by emitting
`capturedMsm_evalNat_ne_zero : capturedMsm.evalNat capturedURS ≠ 0`. The final commit
keeps random proof strings as the motivating caller use without claiming the generic
exporter can attest randomness.

**"chore: more 924 follow-ups"** — documents and locally permits the shared
exporter core's seven required arguments, satisfying Clippy without obscuring them behind
a single-use argument structure.

**orchard 0.15.5 — "Add random match-only fingerprint captures (fabricate→replay)"**
(zcash/orchard#541, merged as `38bd2274`) — adds
`src/circuit/fingerprint/random.rs` (behind the existing `verifier-fingerprint`
feature) and three test drivers. The proof string is produced fabricate→replay so the read
schedule is the deployed verifier's own, never hand-transcribed: a `RandomizingTranscript`
wrapping a real `Blake2bWrite` samples a fresh random canonical value at each
`read_point`/`read_scalar` (points as `generator · t`, `t ≠ 0`), absorbs and buffers it, and
forwards squeezes/common inputs to the inner Blake2b state; the finalized bytes are then
replayed through `ChallengeRecorder` over `Blake2bRead` — identical to the honest pipeline —
and the fixture is exported from the replay. The driver asserts, failing loudly rather than
ever re-seeding silently: verifier ran to completion (twice), replay challenges and
transcript events equal fabrication's, the captured MSM is non-identity on both passes, and
the pinned verifying-key description matches. Public inputs are random raw `F_p` vectors
with the honest captures' shape (one column × ten rows per action). No prover run is
involved: random captures cost one `keygen_vk` plus two verifier passes.

Fabricated points have discrete logs known to the generator. That is harmless here — the
captures are non-accepting and the fixtures witness coefficient agreement only — but it is
recorded for honesty: these are random points of the verifier's input space, not
adversarial proofs.

### Seeds (nothing-up-my-sleeve)

`ChaCha20Rng::from_seed([seed; 32])`, one byte replicated, like the honest captures:

Distributional caveat, stated plainly: fixed public seeds make the fabricated scalars
*constants*, not samples — "nothing up my sleeve" rules out adversarial seed selection but
does not create the uniform distribution the ε theorems count over. Applying the literal ε
therefore assumes that seeded expansion behaves as a uniform sample; this premise is listed in
`Zcash/Snark/Fingerprint/Match.lean`. A reduction-backed alternative would freeze both
implementations, use a future public randomness beacon, regenerate the fixtures, and add the
ChaCha PRG and sampling losses to ε.

| honest two-action | `0x4d` | `M` |
| rejected (Rust-only) | `0x4e` | `N` |
| random single-action | `0x52` | `R` |

### Reproducing

```
scripts/regenerate-fingerprint-fixtures.sh
```

clones `zcash/orchard` at the pinned release commit (set `ORCHARD_SRC` to a local checkout
path for a fully offline run), asserts that the commit is the `0.15.5` tag and that the
committed `Cargo.lock` resolves `halo2_proofs` 0.3.5 from crates.io by checksum, runs the upstream
capture drivers in one pass (five tests — the released orchard also ships a three-action
driver, whose output is not ingested), and diffs every generated artifact against the
committed one. All four fixture families are committed under `Zcash/Snark/Fixtures/`, so
every diff pair is enforced byte-for-byte; a generated artifact with no committed
counterpart yet (a future not-yet-ingested shape) would be stashed in `scripts/generated/`
(gitignored; override with `REGEN_OUT_DIR`). Set `REGEN_WORK_DIR` to reuse the build tree
across runs.

To reproduce by hand instead: check out `zcash/orchard` at tag `0.15.5` and run the capture
drivers with `cargo test --locked --lib --features verifier-fingerprint
circuit::fingerprint::fingerprint_capture`, with the `ORCHARD_LEAN_*_OUT` environment
variables set to the desired output paths. No `Cargo.toml` edit and no lockfile update are
needed: orchard 0.15.5 depends on the released `halo2_proofs` 0.3.5 directly, so the published
lockfile is used as-is. The capture commands are documented on each test driver in
`src/circuit/fingerprint/mod.rs`.
