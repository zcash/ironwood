# Verifier-fingerprint capture provenance

What the captures under `Zcash/Snark/Fixtures/` are, where they come from, and how to
reproduce them. The layout itself is described in `README.md`; what these captures check is each
family's `Boundary.lean` statement of record,
`nonInteractiveFingerprint_matches_derived_keyDigest`. For the unrelated circuit-side dumps see
`Zcash/Circuits/Fixtures/PROVENANCE.md` — the two pipelines share no artifact and no tooling.

Unlike those dumps, these captures have no missing-lineage problem: all four families — the
honest pair and the two match-only families, each of the latter with its raw `proof-bytes.hex`
sibling — regenerate from pinned upstream PR snapshots via
`scripts/regenerate-fingerprint-fixtures.sh`, which CI runs (`fixtures.yml`) to enforce every
committed artifact byte-for-byte.

## The capture sources

The random fixture families (the `Random/` subfolder of `SingleAction` and `MultiAction`)
are captures of the deployed halo2 verifier run on **random proof
strings**. They are generated by the same pipeline as the honest captures — the
`verifier-fingerprint` feature of orchard, forwarding to `halo2_proofs`'
`unstable-verifier-fingerprint`. The base match-only tooling is released in `halo2_proofs` 0.3.5
and orchard 0.15.5 (zcash/halo2#924 and zcash/orchard#541). Carrying the consumed proof bytes,
emitting their hex and the pinned-key preimage directly in each fixture, and testing malformed
encodings through the deployed reader are pinned to the draft follow-ups zcash/halo2#933 and
zcash/orchard#544. These additions remain dev/test tooling behind an unstable feature flag; they
do not alter the deployed verifier.

### The capture changes

`halo2_proofs` 0.3.5 carries the following reviewed source changes (zcash/halo2#924 and its
follow-ups, merged as `475e180e` and released as tag `halo2_proofs-0.3.5`):

**halo2 #924 — "Add a match-only Lean fixture exporter for non-accepting
captures"** — refactors `dump_vesta_lean_fixture`
(`halo2_proofs/src/plonk/fingerprint/vesta_lean.rs`) into a private mode-parameterized core
with two public wrappers. The honest exporter is unchanged in behavior and output. The new
`dump_vesta_lean_fixture_match_only` differs in exactly three places: the identity fail-fast
inverts (the captured MSM must **not** be the identity), the `capturedMsm_eval_eq_zero` /
`assembledMsm_eval_eq_zero` theorems are not emitted, and the generated header marks the
fixture as a match-only capture. Coordinate ordering, on-curve validation, URS emission,
instance-commitment re-derivation, schedule entries, and the slot-reconstruction and
term-count guards are shared with the honest path, so regeneration stays bit-reproducible in
both modes. Two integration tests cover the match-only render and the inverted fail-fast.

**"chore: make the exported fixture claim only what was captured"** —
emits the verifying key's actual `num_instance_columns` count into the generated Lean
`Shape`, defines `capturedNumInstanceColumns` through that field so the two names cannot
drift, and narrows the generic match-only header: the exporter attests only that the
verifier completed with a non-identity MSM, leaving random-input provenance to its caller.
The Orchard driver below supplies and documents that provenance.

**"chore: more 924 followups"** — makes fixture-mode dispatch
exhaustive, repairs the i686 CI package-index setup, and makes each match-only fixture
self-certify its mode by emitting
`capturedMsm_evalNat_ne_zero : capturedMsm.evalNat capturedURS ≠ 0`. The final commit
keeps random proof strings as the motivating caller use without claiming the generic
exporter can attest randomness.

**"chore: more 924 follow-ups"** — documents and locally permits the shared
exporter core's seven required arguments, satisfying Clippy without obscuring them behind
a single-use argument structure.

**orchard 0.15.5 — "Add random match-only fingerprint captures (fabricate→replay)"**
(zcash/orchard#541, merged as `38bd2274`) — adds
`src/circuit/fingerprint/random.rs` (behind the existing `verifier-fingerprint`
feature) and three test drivers. The proof string is produced fabricate→replay so the read
schedule is the deployed verifier's own, never hand-transcribed: a `RandomizingTranscript`
wrapping a real `Blake2bWrite` samples a fresh random canonical value at each
`read_point`/`read_scalar` (points as `generator · t`, `t ≠ 0`), absorbs and buffers it, and
forwards squeezes/common inputs to the inner BLAKE2b state; the finalized bytes are then
replayed through `ChallengeRecorder` over `Blake2bRead` — identical to the honest pipeline —
and the fixture is exported from the replay. The driver asserts, failing loudly rather than
ever re-seeding silently: verifier ran to completion (twice), replay challenges and
transcript events equal fabrication's, the captured MSM is non-identity on both passes, and
the pinned verifying-key description matches. Public inputs are random raw `F_p` vectors
with the honest captures' shape (one column × ten rows per action). No prover run is
involved: random captures cost one `keygen_vk` plus two verifier passes.

**halo2 #933 — "Carry the consumed proof bytes in Lean fixture exports"** adds honest and
match-only `_with_proof_bytes` exporters. They reserialize every recorded point/scalar read and
require byte equality with the supplied proof before emitting `capturedProofHex`. At the pinned
head, every fixture also carries `capturedPinnedKeyDescription`, the exact compact `Debug` string
hashed into `transcript_repr`, after the exporter re-hashes it and checks that scalar.

**orchard #544 — "Pass the consumed proof bytes to the fingerprint fixture exporters"** routes
the honest proof and fabricated random strings through those APIs. Each random driver additionally
applies the six edits mirrored in `ProofBytes.lean` to its exact deterministic proof: truncation,
a scalar encoded as value plus modulus, identity, an out-of-range coordinate, a non-residue `x`,
and a flipped point-sign bit. The first five must reject through deployed `Blake2bRead`; the last
must decode to the negated point.

Fabricated points have discrete logs known to the generator. That is harmless here — the
captures are non-accepting and the fixtures witness coefficient agreement only — but it is
recorded for honesty: these are random points of the verifier's input space, not
adversarial proofs.

### Seeds (nothing-up-my-sleeve)

`ChaCha20Rng::from_seed([seed; 32])`, one byte replicated, like the honest captures:

Distributional caveat, stated plainly: fixed public seeds make the fabricated scalars
*constants*, not samples — "nothing up my sleeve" rules out adversarial seed selection but
does not create the uniform distribution the ε theorems count over. Applying the literal ε
therefore assumes that seeded expansion behaves as a uniform sample; this premiss is listed in
`Zcash/Snark/Fingerprint/Match.lean`. A reduction-backed alternative would freeze both
implementations, use a future public randomness beacon, regenerate the fixtures, and add the
ChaCha PRG and sampling losses to ε.

### The manifest

`MANIFEST.tsv` records each committed capture's provenance in one machine-checkable row —
path, sha256, generator, source revision, invocation. `scripts/check_fixture_manifest.sh`
(run by the fixtures workflow on every push and pull request) verifies the digests and
rejects any generated-looking artifact that lacks an entry, so the committed bytes stay
bound to their recorded provenance between full regenerations. Editing a capture means
regenerating it and updating its manifest row in the same change.

### Generated proof bytes

The capture APIs make the fixture mode explicit in their names: accepting captures use
`dump_vesta_lean_fixture_honest_with_proof_bytes`, while non-accepting captures use
`dump_vesta_lean_fixture_match_only_with_proof_bytes`. `capturedProofHex` now comes directly from
the generated `Fixture.lean`; the former rendered `ProofHex.lean` modules are gone. The random
families retain `proof-bytes.hex` as a non-Lean sibling emitted from the same `proof_bytes` value.
Both artifacts are manifest-pinned and full regeneration diffs them byte-for-byte.

Each honest family's `ProofBytes.lean` parses its generated bytes back to the captured typed proof
and composes that exact parse, the derived pinned-key digest, and BLAKE2b challenge derivation into
`DeployedAcceptsBytes`, discharging by evaluation its key identification (`Describes`: the emitted
description's fields are the captured key's and shape's) and its exclusion of identity instance
commitments. The random families use the same parser for the non-accepting captures and
the rejection cases below.

### Rejection coverage at the PR pins

The Lean decoder and deployed Rust reader exercise the same exact deterministic edits. This is
strong per-capture evidence and source alignment, not a universal refinement theorem:

| Case | Lean proof-byte fixture | Orchard #544 deployed run |
|---|---|---|
| exact captured random proof | parses to the captured `ProofString`; serialization is checked | the random driver fabricates and replays it through `Blake2bRead` |
| final scalar truncated by one byte | rejected by `readProof?` | rejected by `read_scalar` on the same final slice |
| scalar encoded as value plus modulus | rejected by `readProof?` | rejected by `read_scalar` on the same edit |
| identity compressed point | rejected by `readProof?` | rejected by `read_point` on the same edit |
| coordinate equal to the base-field modulus | rejected by `readProof?` | rejected by `read_point` on the same edit |
| non-residue compressed `x` | rejected by `readProof?` | rejected by `read_point` on the same edit |
| flipped point-sign bit | decodes to the negated point | decodes to the negated captured point |

Separately, `fingerprint_rejected_capture_two_actions` changes a well-formed advice evaluation and
observes final semantic rejection, truncates a multiopen stream, and skips a permutation scalar so
later reads desynchronize. Those remain separate semantic and stream-alignment rejection paths;
the exact malformed-element assertions above run inside both pinned random capture drivers.

### The pinned key description

The pinned #933 exporter computes `format!("{:?}", self.pinned())`, the exact compact text Halo2
hashes into `transcript_repr`. Before emitting it as `capturedPinnedKeyDescription`, the exporter
repeats the `Halo2-Verify-Key` hash and checks that it reproduces the scalar. Each family's
`Transcript.lean` independently repeats that hash. `PinnedKey.lean` additionally parses the honest
single-action string and compares its fields with the captured key; the keygen certificate connects
that captured key to the Lean-derived verifier key. Thus the captured scalar is checked rather than
trusted, while the description string and captured key remain fixture inputs.

### Reproducing

```
scripts/regenerate-fingerprint-fixtures.sh
```

clones `zcash/orchard` at the pinned #544 commit (set `ORCHARD_SRC` to a local checkout containing
that commit to clone Orchard locally), verifies and normalizes its temporary Halo2 Cargo patch to
the canonical pinned #933 SHA, runs every Cargo command `--locked`, and executes the upstream
capture drivers in one pass (five tests — Orchard also ships a three-action
driver, whose output is not ingested), and diffs every generated artifact against the
committed one. All four fixture families are committed under `Zcash/Snark/Fixtures/`, so
every diff pair is enforced byte-for-byte; a generated artifact with no committed
counterpart yet (a future not-yet-ingested shape) would be stashed in `scripts/generated/`
(gitignored; override with `REGEN_OUT_DIR`). Set `REGEN_WORK_DIR` to reuse the build tree
across runs.

To reproduce by hand instead: check out the Orchard SHA above, replace its asserted temporary
Halo2 patch with the canonical URL and #933 SHA exactly as the script does, and run `cargo test
--locked --lib --features verifier-fingerprint circuit::fingerprint::fingerprint_capture` with
the `ORCHARD_LEAN_*_OUT` environment variables set to the desired output paths. The capture
commands are documented on each test driver in `src/circuit/fingerprint/mod.rs`.
